## 大歌单（>200 首）原地重排（commit 41080c8 / 31b16d1）

**根因**：`playlist reorder` 把 ID 拼进 URL，≈235 个 ID（7.7KB）就撞上 8KB 上限被拒。
ncm-cli 0.1.7 已核对：参数没变、无分片选项，官方没解法。

**两条路径**（`ncm_reorder_any` 自动选路）：
1. 直连接口（首选，保留入库时间）：`POST https://music.163.com/api/playlist/track/update`
   老明文接口、ids 在 body → 无长度上限。需要 `MUSIC_U`+`__csrf`；
   Cookie 来源：~/.config/ncm-cli/session/storage-state.json（0.1.7 Playwright 登录生成，明文）
   或设置里手动粘贴（config.json 的 ncm_cookie，不进仓库）。
   注意老接口要**数字 ID**（originalId），不是 enc id。
2. 分步重排（回退，无需 cookie）：reorder 只留目标顺序尾部 ≤200 首（一次请求）
   → 目标顺序前段每 100 首一批 add 回去（add 是「前插」，所以要**倒序处理批次**）
   → 读回校验。副作用：被 add 的歌「入库时间」刷新；整批失败会返回 missing。

**踩坑**：
- 分批 add 到已有歌单时批次必须倒序（每批都前插），否则整体顺序会错位
- ncm-cli 0.1.3 的凭据（credentials.enc.json / tokens.enc.json）解不开：
  DPAPI 用各种 description/entropy 组合都是 Error 13（官方 CLI 自行混了 AES），别再试
- `ncm_reorder` 加了 batch_size 参数：尾部 200 首一次发完，省 6 次请求

**验证状态**：模拟 ncm-cli 语义的自动化测试全过（4374 首倒序 → 43 次请求顺序逐项一致；
小歌单/重复ID/批次失败/直连回退均正确）。**真机未验证**（登录态过期 + 无 cookie）。

## 修正：大歌单重排方案（commit de67a28）—— 真机实测推翻了旧假设

**用户反馈「排的顺序不对」**。在临时测试歌单（新建、测完清空）上做了 6 组实验，
实测出 ncm-cli 的真实行为（AGENTS.md 已记录，务必先读）：

- `reorder` **必须传完整列表**才生效，传子集返回 200 但顺序**完全不变**（静默忽略）
  → 旧方案「reorder 尾部 200 + add 前段」第一步根本没生效，第二步 add 又前插 170 首
  → 歌单变成 540 首且顺序错乱。**这就是「顺序不对」的根因**
- `remove --songIdList` **必须 JSON 数组**（逗号分隔报 readObject 出错），单次也不能太长
- `add` 前插 + 批内倒序；倒序处理批次后顺序正确（370 首实测 100% 一致）
- reorder 逗号分隔格式**有效**（不是 JSON 数组）；370 个 ID = 12210 字符 → "参数太长"

**正确方案**：remove 分批清空 → add 分批写回 → 读回逐项校验。
